# 9 октября 2026 — домен не резолвился, сертификат не выпускался

Полдня на то, чтобы поднять `https://vsluh.club`. Корень один, последствий несколько.

## Симптом

Домен выглядел «не прописавшимся»: сайт на GitHub Pages работал, DNS-записи в Cloudflare
стояли правильные, но браузер домен не открывал.

```
dig +short A vsluh.club @1.1.1.1   → пусто
dig +short A vsluh.club @8.8.8.8   → пусто
dig +short A vsluh.club @77.88.8.8 → 185.199.108.153 ...   ← Яндекс отвечает
```

Первая гипотеза (негативный кэш после недавней регистрации) оказалась **неверной** —
и стоила лишнего часа ожидания.

## Настоящая причина

Статус ответа был не `NXDOMAIN`, а **`SERVFAIL`**. Это признак сломанного DNSSEC,
а не отсутствия записи.

```
dig vsluh.club A @1.1.1.1 +noall +comments | grep status
;; ->>HEADER<<- opcode: QUERY, status: SERVFAIL
```

Проверка без валидации подтвердила догадку — данные на месте, отвергает их именно валидатор:

```
dig +short +cd A vsluh.club @1.1.1.1 → 185.199.108.153 ...
```

В реестре `.club` висела DS-запись от прежнего подписанта, а зона на Cloudflare
подписана не была:

```
dig DS vsluh.club @a.nic.club → 30543 13 2 0149ED6C...   ← чужой ключ
```

Цепочка доверия рвалась, и все валидирующие резолверы (1.1.1.1, 8.8.8.8, 9.9.9.9)
отказывались отдавать ответ. Яндекс отвечал, потому что DNSSEC не проверяет.

## Почему не заметили сразу

`whois` отдаёт **две противоречащие строки** — от реестра и от регистратора:

```
DNSSEC: signedDelegation   ← реестр .club: DS есть
DNSSEC: unsigned           ← Namecheap: в панели выключено
```

В панели Namecheap переключатель DNSSEC был **выключен**, а таблица DS-записей пуста.
Запись в реестре при этом существовала. Увидеть её удалось, только включив тумблер —
тогда таблица подтянула залипшую `30543`.

Вывод: панели регистратора верить нельзя, проверять через `dig ... @a.nic.club`.

## Что сделали

1. Включили DNSSEC в Cloudflare и забрали DS:

   ```bash
   curl -s -X PATCH -H "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
     -H "Content-Type: application/json" \
     "https://api.cloudflare.com/client/v4/zones/$ZONE/dnssec" --data '{"status":"active"}'
   ```

   Ключ сверили с тем, что реально отдают серверы зоны:

   ```bash
   dig DNSKEY vsluh.club @ivan.ns.cloudflare.com +multi | grep 'key id'
   # KSK key id = 2371
   ```

2. В Namecheap включили DNSSEC, добавили DS `2371 / 13 / 2 / 407107C7…96327`
   и удалили чужую `30543`.

3. Через ~5 минут реестр обновился, резолв ожил на всех публичных DNS.

## Второй акт: сертификат

Домен заработал, но HTTPS — нет. GitHub Pages держал `bad_authz`, а на 443 отдавался
дефолтный `CN=*.github.io`.

Проверка Certificate Transparency показала, что **сертификат не выпускался ни разу**:

```bash
curl -s "https://crt.sh/?q=vsluh.club&output=json"   # пустой ответ
```

То есть ACME не доходил до выдачи — логично, пока домен не резолвился, валидация
владения падала.

Но и после починки DNS выпуск не пошёл. Причина — **наши же действия**: за полчаса
ACME перезапускали восемь раз плюс дважды пересоздавали Pages. У Let's Encrypt лимит
5 неудачных валидаций на домен в час, мы в него упёрлись и заблокировали сами себя.

## Решение: Cloudflare вместо GitHub

Переключили TLS на Cloudflare — все записи в режим `proxied: true`:

```
A      vsluh.club      → 185.199.108-111.153   proxied=true
CNAME  www.vsluh.club  → sofiaboop.github.io   proxied=true
```

HTTP сразу пошёл через Cloudflare (`Server: cloudflare`), но TLS рвался:

```
SSL alert number 40 — handshake failure
no peer certificate available
```

Universal SSL был в статусе `pending_validation` — Cloudflare ждал подтверждения
через TXT `_acme-challenge.vsluh.club`. Записи уже отдавались публичным DNS
(Cloudflare держит их скрытыми от списка записей зоны), то есть валидация шла.

Сертификат выпустился **ровно через час после починки DNSSEC** — на первой же
повторной попытке Cloudflare:

```
subject = CN=vsluh.club
issuer  = Let's Encrypt YE1
```

## Чуть не положили сайт

Включили `Always Use HTTPS` до выпуска сертификата. Редирект отправлял бы всех
посетителей на нерабочий протокол. Поймали на проверке и откатили за полминуты —
сайт по HTTP продолжал отвечать 200.

Правильный порядок: сертификат → проверка `https` → только потом редирект.

## Итоговая конфигурация

| Параметр           | Значение |
| ------------------ | -------- |
| SSL mode           | `full`   |
| Universal SSL      | on, Let's Encrypt |
| Always Use HTTPS   | on (включено после выпуска) |
| Minimum TLS        | `1.2`    |
| DNSSEC             | active, key tag `2371` |

Файл `public/CNAME` из репозитория убрали: в артефакте деплоя он переустанавливает
кастомный домен при каждом пуше и сбрасывает процесс выпуска сертификата.
Домен задаётся в настройках Pages.

## Чему научились

- `SERVFAIL` ≠ «ещё не распространилось». Это почти всегда DNSSEC.
- `dig +cd` — первый инструмент: отделяет проблему данных от проблемы валидации.
- Реестр и регистратор — разные источники, сверять оба.
- Выпуск сертификата не ускоряется перезапусками, а только ломается ими.
- Любой редирект на HTTPS включать последним шагом, после фактической проверки.
